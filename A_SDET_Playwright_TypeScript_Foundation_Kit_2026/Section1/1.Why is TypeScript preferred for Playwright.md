# Q1. Why is TypeScript the preferred language for Playwright automation?

### ✅ English Interview Answer

> “TypeScript is preferred for Playwright automation because it provides static typing, compile-time error detection, better IDE autocomplete, and maintainability. Playwright also provides TypeScript definitions, so we get type safety across locators, API calls, fixtures, and page objects. In CI, I can use `tsc --noEmit` to detect type errors before running the browser tests.”

## 🔍 Internal Concept — How it works internally

Think of the execution flow like this:

```text
TypeScript Code
      ↓
TypeScript Compiler
      ↓
Type Checking
      ↓
Compile Errors? ── Yes → STOP ❌
      ↓ No
JavaScript / Test Execution
      ↓
Playwright
      ↓
Browser
```

For example:

```typescript
function login(username: string) {
  console.log(username);
}
```

Correct:

```typescript
login("admin");
```

Incorrect:

```typescript
login(12345);
```

TypeScript identifies:

```text
Argument of type 'number'
is not assignable to parameter of type 'string'
```

The important point is that this error can be caught **before the browser launches**. The Foundation Kit specifically describes compile-time error detection as one of TypeScript's major advantages.

# 💼 Real-Time SDET Project Example

Suppose mana Playwright framework lo common login function undi.

```typescript
import { Page } from "@playwright/test";

async function login(
  page: Page,
  username: string,
  password: string,
): Promise<void> {
  await page.getByLabel("Username").fill(username);

  await page.getByLabel("Password").fill(password);

  await page.getByRole("button", { name: "Login" }).click();
}
```

Test case:

```typescript
test("Valid Login", async ({ page }) => {
  await login(page, "admin@test.com", "Admin@123");
});
```

Here TypeScript checks:

- `page` must be a `Page`
- `username` must be a `string`
- `password` must be a `string`
- `login()` returns a `Promise<void>`

So our framework becomes more reliable and maintainable.

# 💻 Code — Playwright + TypeScript

```typescript
import { test, expect, Page } from "@playwright/test";

async function login(
  page: Page,
  username: string,
  password: string,
): Promise<void> {
  await page.getByLabel("Username").fill(username);

  await page.getByLabel("Password").fill(password);

  await page.getByRole("button", { name: "Login" }).click();
}

test("User Login", async ({ page }) => {
  await page.goto("/login");

  await login(page, "admin@test.com", "Admin@123");

  await expect(page.getByText("Dashboard")).toBeVisible();
});
```

### Important interview points

**`page: Page`**

Means the parameter must be a Playwright `Page`.

**`username: string`**

Username must be a string.

**`password: string`**

Password must be a string.

**`Promise<void>`**

The function is asynchronous and doesn't return a value.

**`await`**

Waits for asynchronous Playwright operations.

# 🎯 Follow-up Questions Interviewer May Ask

### Q1. What is the main difference between JavaScript and TypeScript?

**Answer:**

> “JavaScript is dynamically typed, whereas TypeScript adds static typing and compile-time type checking.”

### Q2. When are TypeScript errors detected?

**Answer:**

> “Primarily during compile-time/type-checking, before the tests execute.”

### Q3. How do you type-check a TypeScript Playwright project?

**Answer:**

```bash
tsc --noEmit
```

The Foundation Kit recommends using this as an early CI gate.

### Q4. Why is autocomplete useful in Playwright?

**Answer:**

> “Playwright provides TypeScript definitions, so the IDE can show available methods, parameters, and return types while writing automation code.”

### Q5. Why is TypeScript useful in a large automation framework?

**Answer:**

> “It makes contracts explicit, helps identify broken call sites when types change, improves refactoring, and makes the code easier to maintain.”
