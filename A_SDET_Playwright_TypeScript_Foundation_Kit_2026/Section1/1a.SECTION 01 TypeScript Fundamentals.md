## Q1. Why is TypeScript preferred for Playwright automation?

### ✅ Interview Answer — English

> **“TypeScript is preferred for Playwright because it provides static typing, compile-time error detection, better IDE autocomplete, and maintainable contracts. Playwright provides TypeScript definitions, so we get type safety while writing locators, API calls, fixtures, and page objects. In CI, I use `tsc --noEmit` to catch type errors before executing browser tests.”**

### 🔍 How it works internally

JavaScript:

```typescript
login(page, 12345, true);
```

JavaScript may allow incorrect values until runtime.

TypeScript:

```typescript
async function login(
  page: Page,
  email: string,
  password: string,
): Promise<void> {
  await page.getByLabel("Email").fill(email);
}
```

Now:

```typescript
login(page, 12345, true);
```

gives a **compile-time error** because `email` expects a string.

### 🇮🇳 Telugu

TypeScript అంటే JavaScript + **type safety**.

Automation project lo mistakes browser open ayyaka కాకుండా **compile time lone catch** cheyyachu.

Benefits:

- Autocomplete
- Type safety
- Maintainability
- Compile-time errors
- Better refactoring
- CI lo early failure

### 💼 Real-time project

Suppose API response:

```typescript

  id: number;
  name: string;
  email: string;
}
```

# Q2. Interface vs Type — difference?

### ✅ Interview Answer — English

> **“Both interfaces and type aliases can describe object shapes. I generally use interfaces for contracts that classes or page objects extend or implement, and types for unions, intersections, and utility-type derivations. In a framework, I prefer defining a domain model once and deriving related request types using `Omit`, `Partial`, or `Pick`.”**

### 🔍 Concept

**Interface:**

```typescript
interface BasePage {
  navigate(url: string): Promise<void>;
}

interface LoginPage extends BasePage {
  login(email: string): Promise<void>;
}
```

**Type:**

```typescript
type Environment = "dev" | "staging" | "production";
```

**Omit:**

```typescript
interface UserResponse {
  id: number;
  name: string;
  email: string;
  createdAt: string;
}

type CreateUserRequest = Omit<UserResponse, "id" | "createdAt">;
```

**Partial:**

```typescript
type UpdateUserRequest = Partial<CreateUserRequest>;
```

These patterns are specifically highlighted in the kit as a way to keep API contracts synchronized.

### 🇮🇳 Telugu

Simple ga:

**Interface → class/page object contract**

**Type → union / utility / derived types**

Example:

```typescript
type Browser = "chromium" | "firefox" | "webkit";
```

### 💼 Real project

API response:

```text
UserResponse
   ↓
Omit
   ↓
CreateUserRequest
   ↓
Partial
   ↓
UpdateUserRequest
```

Backend contract change ayithe compiler affected tests ni identify chestundi.

### 🎯 Follow-up

**Q: Can interface extend interface?**
Yes.

**Q: Can type represent union?**
Yes.

```typescript
type Role = "Admin" | "User";
```

### 🧠 Remember

**Interface = Implement/Extend**

**Type = Union/Utility**

# Q3. How do async/await work, and why does missing await break Playwright?

### ✅ Interview Answer — English

> **“Playwright browser actions are asynchronous and return Promises. `async/await` allows me to write those operations sequentially while they execute asynchronously underneath. If I miss `await`, the next statement can execute before the previous operation finishes, causing race conditions and flaky tests.”**

### ❌ Wrong

```typescript
test("login", async ({ page }) => {
  page.goto("/login");
  page.fill("#email", "admin");
});
```

### ✅ Correct

```typescript
test("login", async ({ page }) => {
  await page.goto("/login");
  await page.fill("#email", "admin");
});
```

### 💼 Real-time API example

Button click triggers API:

```typescript
const [response] = await Promise.all([
  page.waitForResponse("**/api/login"),

  page
    .getByRole("button", {
      name: "Sign in",
    })
    .click(),
]);

expect(response.status()).toBe(200);
```

Important: **listen first → click second**.

### 🇮🇳 Telugu

`await` అంటే:

> **“Ee operation complete ayye varaku next line ki vellaku.”**

Missing await → race condition → flaky test.

### 🧠 Remember

**Async action → Promise → Await → Continue**

# Q4. What are TypeScript Generics?

### ✅ Interview Answer — English

> **“Generics allow me to write reusable functions or classes that work with different types while maintaining type safety. In Playwright frameworks, I commonly use generics for typed API clients and test-data factories.”**

### 💻 Real-time API client

```typescript
async function apiGet<T>(request: APIRequestContext, url: string): Promise<T> {
  const response = await request.get(url);

  return await response.json();
}
```

Usage:

```typescript
interface User {
  id: number;
  name: string;
}

const user = await apiGet<User>(request, "/users/1");

console.log(user.name);
```

One function → many response types.

### Test-data factory

```typescript
function createTestData<T>(defaults: T, overrides?: Partial<T>): T {
  return {
    ...defaults,
    ...overrides,
  };
}
```

### 🇮🇳 Telugu

Generic ante:

> **Oka function ni different data types kosam reusable ga maintain cheyyadam.**

`<T>` = type placeholder.

### 🧠 Remember

**Generic = Reusable + Type Safe**

# Q7. How do you configure path aliases?

### ✅ Interview Answer — English

> **“I use `paths` in `tsconfig.json` to create stable aliases for commonly used directories. This avoids fragile relative imports such as `../../../pages/LoginPage` and makes the framework easier to maintain when folders move.”**

### 💻 tsconfig

```json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@pages/*": ["src/pages/*"],
      "@utils/*": ["src/utils/*"],
      "@types/*": ["src/types/*"]
    }
  }
}
```

Instead of:

```typescript
import { LoginPage } from "../../../src/pages/auth/LoginPage";
```

Use:

```typescript
import { LoginPage } from "@pages/auth/LoginPage";
```

### 🇮🇳 Telugu

Path alias ante:

**Long relative path → short meaningful alias**

### 💼 Project structure

```text

 ├── pages/
 ├── utils/
 ├── types/

```

# Q11. What is the `satisfies` operator?

### ✅ Interview Answer — English

> **“The `satisfies` operator validates that an object matches a required type while preserving the object's narrower inferred types. Unlike a type annotation, it doesn't unnecessarily widen the values, and unlike `as`, it performs actual compatibility checking.”**

### 💻 Example

```typescript
interface ProjectConfig {
  name: string;
  viewport: {
    width: number;
    height: number;
  };
}

const config = {
  name: "chromium",
  viewport: {
    width: 1280,
    height: 720,
  },
} satisfies ProjectConfig;
```

Now TypeScript validates the structure while retaining narrow information such as the literal `'chromium'`.

### 🇮🇳 Telugu

`satisfies` ante:

> **“Ee object ee type rules follow chestunda check cheyyi, but original narrow type information ni preserve cheyyi.”**

### 🧠 Remember

**satisfies = Validate + Preserve**

# Q12. What are discriminated unions?

### ✅ Interview Answer — English

> **“A discriminated union is a union of object types that share a literal discriminator property. TypeScript uses that property to automatically narrow the object to the correct type inside a switch or conditional.”**

### 💻 Example

```typescript
type TestResult =
  | { status: "passed"; duration: number }
  | { status: "failed"; error: string }
  | { status: "skipped"; reason: string };

function report(result: TestResult) {
  switch (result.status) {
    case "passed":
      return result.duration;

    case "failed":
      return result.error;

    case "skipped":
      return result.reason;
  }
}
```

TypeScript automatically understands which properties exist for each state.

### 💼 Real project

Useful for:

```text
Test Result
 ├── Passed
 ├── Failed
 └── Skipped
```

### 🇮🇳 Telugu

Common field:

```typescript
status;
```

దాని value batti TypeScript correct object ni identify chestundi.

### 🧠 Remember

**Discriminator → Narrowing**

# Q13. What are Type Guards?

### ✅ Interview Answer — English

> **“A type guard is a runtime check that allows TypeScript to safely narrow an unknown value to a specific type. I commonly use type guards when validating API responses because `response.json()` can contain untrusted runtime data.”**

### 💻 Example

```typescript
interface ApiUser {
  id: number;
  email: string;
}

function isApiUser(value: unknown): value is ApiUser {
  return (
    typeof value === "object" &&
    value !== null &&
    "id" in value &&
    "email" in value
  );
}
```

Usage:

```typescript
const raw: unknown = await response.json();

if (!isApiUser(raw)) {
  throw new Error("Invalid API response");
}

console.log(raw.email.toLowerCase());
```

After the guard, TypeScript knows `raw` is `ApiUser`.

### 🇮🇳 Telugu

API nundi vachina data ni blindly trust cheyyakunda:

```text
unknown data
   ↓
Type Guard
   ↓
Known type
```

### 🧠 Remember

**Guard = Check before use**

# Q14. What are branded types?

### ✅ Interview Answer — English

> **“Branded types provide nominal-like safety on top of TypeScript's structural type system. They are useful when two IDs are both strings but represent different domain objects, such as UserId and OrderId.”**

### 💻 Example

```typescript
type UserId = string & { readonly __brand: "UserId" };

type OrderId = string & { readonly __brand: "OrderId" };

function UserId(value: string): UserId {
  return value as UserId;
}

function OrderId(value: string): OrderId {
  return value as OrderId;
}
```

Now:

```typescript
const user = UserId("u_123");
const order = OrderId("o_789");

async function deleteOrder(id: OrderId) {}

deleteOrder(order); // ✅
deleteOrder(user); // ❌
```

The kit uses this exact pattern to prevent ID mix-ups.

### 🇮🇳 Telugu

Rendu values:

```text
UserId = string
OrderId = string
```

Technically same shape.

But business meaning different.

Branded type compiler ki:

> “These are different IDs.”

ani cheptundi.

### 🧠 Remember

**Brand = Same shape, different meaning**

# Q15. What are mapped types?

### ✅ Interview Answer — English

> **“Mapped types create a new type by iterating over the properties of an existing type and transforming them. They are useful for automatically generating related types such as getters, optional fields, readonly models, or API variants.”**

### 💻 Example

```typescript
interface User {
  id: number;
  name: string;
  email: string;
}

type ReadonlyUser = {
  readonly [K in keyof User]: User[K];
};
```

Partial:

```typescript
type PartialUser = {
  [K in keyof User]?: User[K];
};
```

These patterns are shown in the section's mapped-type examples.

# Q17. What is `never` and exhaustive switch?

### ✅ Interview Answer — English

> **“`never` represents a value that should never occur. In a discriminated union, I use `never` in a default branch to enforce exhaustive handling. If a new state is added and the switch doesn't handle it, TypeScript reports a compile-time error.”**

### 💻 Example

```typescript
type Status = "passed" | "failed" | "skipped";

function assertNever(value: never): never {
  throw new Error(`Unexpected value: ${value}`);
}
```

Use:

```typescript
function report(status: Status) {
  switch (status) {
    case "passed":
      return "PASS";

    case "failed":
      return "FAIL";

    case "skipped":
      return "SKIPPED";

    default:
      return assertNever(status);
  }
}
```

If someone adds:

```typescript
| 'blocked'
```

but forgets to handle it, the compiler catches the problem. The kit specifically describes this exhaustive-switch pattern.

### 🇮🇳 Telugu

`never` means:

> **“Ee situation normally jaragakudadhu.”**

New status add chesi switch lo handle cheyyakapothe compiler error.

### 🧠 Remember

**never = No case left behind**

# Q18. What is declaration merging?

### ✅ Interview Answer — English

> **“Declaration merging allows TypeScript to combine multiple declarations with the same name. In Playwright, this can be used through module augmentation to extend existing Playwright types with custom methods or matchers while retaining autocomplete and type safety.”**

The section introduces declaration merging specifically in the context of extending Playwright's `test` and `expect`.

### 💻 Simple TypeScript example

```typescript
interface User {
  name: string;
}

interface User {
  email: string;
}
```

TypeScript merges them into:

```typescript
interface User {
  name: string;
  email: string;
}
```

### 💼 Real Playwright use case

Suppose your framework wants a custom assertion:

```typescript
await expect(page).toHaveValidLoginState();
```

You can augment Playwright's types so TypeScript understands the custom matcher instead of showing a type error.

### 🇮🇳 Telugu

Declaration merging అంటే:

**Same name declarations → TypeScript combine chestundi.**
