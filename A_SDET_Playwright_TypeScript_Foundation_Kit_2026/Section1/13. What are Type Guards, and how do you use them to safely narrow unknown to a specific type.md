# Q13. What are Type Guards, and how do you use them to safely narrow `unknown` to a specific type?

This is a **Mid-level TypeScript question** from your Foundation Kit. The main focus is **safely handling external data** such as API responses, JSON, `postMessage`, and `localStorage` data.

---

## ✅ English Interview Answer

> **“A type guard is a function that safely checks whether an unknown value matches a specific type. It uses a type predicate such as `obj is ApiUser`. This tells TypeScript that if the function returns true, the object can be treated as that type. In an SDET framework, I use type guards at external-data boundaries, especially for API responses and JSON data, instead of blindly using `as`. This helps catch malformed data before it causes runtime failures.”**

### ⭐ Short Interview Answer

> **“A type guard validates an `unknown` value and safely narrows it to a specific type using a type predicate like `obj is User`.”**

# 🔍 Internal Concept — How It Works

Suppose API nundi data vachindi:

```typescript
const raw: unknown = await response.json();
```

Why `unknown`?

Because TypeScript doesn't know whether the API actually returned the expected structure.

```text id="a91k2m"
API Response
     ↓
   unknown
     ↓
Type Guard
     ↓
Valid? ── No → Error ❌
     │
    Yes
     ↓
  ApiUser
     ↓
Safe access ✅
```

A type guard has this important return type:

```typescript
obj is ApiUser
```

This is called a **type predicate**.

---

# 💻 Real-Time SDET Example — API Response

Suppose our API should return:

```typescript
interface ApiUser {
  id: number;
  email: string;
  isAdmin: boolean;
}
```

But APIs can sometimes return unexpected data.

So we create:

```typescript
function isApiUser(obj: unknown): obj is ApiUser {
  if (typeof obj !== "object" || obj === null) {
    return false;
  }

  const user = obj as Record<string, unknown>;

  return (
    typeof user.id === "number" &&
    typeof user.email === "string" &&
    typeof user.isAdmin === "boolean"
  );
}
```

This follows the Foundation Kit's recommended pattern: **object check → null check → `Record<string, unknown>` → validate each field**.

# 💻 Using the Type Guard in Playwright API Testing

```typescript
const raw: unknown = await response.json();

if (!isApiUser(raw)) {
  throw new Error(`Malformed user response: ${JSON.stringify(raw)}`);
}

console.log(raw.email.toLowerCase());
```

After:

```typescript

```

TypeScript knows:

```text id="m4x8p2"

 ↓
ApiUser
 ↓
id       → number
email    → string
isAdmin  → boolean
```

So:

```typescript
raw.email.toLowerCase();
```

is safe.

# ❌ Why Not Just Use `as`?

A common mistake:

```typescript
const user = (await response.json()) as ApiUser;
```

Many developers think this means:

> “Convert the response into `ApiUser`.”

But that's **not what `as` does**.

It only tells the compiler:

> “Trust me, this is an `ApiUser`.”

It does **not validate the actual runtime data**.

---

# 🚨 Example of the Problem

API returns:

```json
{
  "id": "ABC",
  "email": 123
}
```

But we write:

```typescript
const user = (await response.json()) as ApiUser;

console.log(user.email.toLowerCase());
```

TypeScript may accept it.

But at runtime:

```text id="z8c4m1"
email = 123
   ↓
toLowerCase()
   ↓
💥 Runtime error
```

### Important interview statement:

> **“`as` silences the compiler; it doesn't validate or change the runtime value.”**

# 🎯 Follow-up Questions Interviewer May Ask

### Q1. What is a type predicate?

> **“A type predicate is a return type such as `obj is ApiUser` that tells TypeScript the value has that type when the function returns true.”**

Example:

```typescript
function isApiUser(obj: unknown): obj is ApiUser {
  // validation
}
```

---

### Q2. Why use `unknown` instead of `any`?

### ⭐ Strong Answer

> **“`unknown` is safer because TypeScript doesn't allow arbitrary operations on it until we narrow it to a known type. `any` effectively disables type checking.”**

### Telugu:

> **“`unknown` lo direct ga properties or methods access cheyyalem. First type validate cheyyali. `any` use chesthe type safety chala varaku disable avutundi.”**

---

### Q3. Where should validation happen?

> **“At the boundary where external data enters the application or test framework.”**

For example:

```text id="n3f8v2"
API
 ↓
Type Guard
 ↓
Typed application
```

Not:

```text id="j6q1r9"
API
 ↓
Use everywhere
 ↓
Validate later ❌
```

The Foundation Kit calls this the **boundary between your code and the outside world**.

---

### Q4. Does a type guard change the runtime object?

> **“No. It validates the value and gives TypeScript information for type narrowing. It doesn't magically transform the object.”**

---

### Q5. What is the difference between a type guard and `as`?

| Type Guard             | `as`                        |
| ---------------------- | --------------------------- |
| Validates data         | Doesn't validate            |
| Runtime checks         | Compile-time assertion      |
| Safely narrows         | Tells compiler to trust you |
| Good for external data | Dangerous if used blindly   |

### 🔥 Interview line:

> **“Type guard proves the shape; `as` only claims the shape.”**
