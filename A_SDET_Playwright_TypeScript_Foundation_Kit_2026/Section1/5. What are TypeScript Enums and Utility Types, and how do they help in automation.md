# Q5. What are TypeScript Enums and Utility Types, and how do they help in automation?

The Foundation Kit emphasizes two main benefits: **Enums remove magic-string mistakes**, while **utility types prevent duplicated type definitions**. It also highlights a senior-level pattern: using a **`Record` keyed by an enum** to make test data exhaustive.

---

## ✅ English Interview Answer

> **“Enums allow us to replace magic strings with named constants, which helps prevent typo-related test-data bugs. Utility types allow us to derive new types from existing interfaces instead of duplicating them. For example, `Partial` makes properties optional, `Omit` removes properties, `Pick` selects properties, and `Record` creates a typed key-value map. In automation, I particularly use a `Record` keyed by an enum for credentials or test data because TypeScript enforces that every role has an entry.”**

### ⭐ Short Interview Answer

> **“Enums remove magic-string errors, utility types reduce type duplication, and `Record<Enum, Type>` helps ensure test data is complete.”**

# 🔍 Internal Concept — How It Works

Suppose we write:

```typescript id="jgr0ai"
const role = "admin";
```

Another developer might write:

```typescript id="o9v0de"
const role = "Admin";
```

Both look similar, but they are **different strings**.

This can create runtime test failures.

Instead, define:

```typescript id="8z7l8u"
enum UserRole {
  Admin = "admin",
  User = "user",
  Viewer = "viewer",
}
```

Now:

```typescript id="y9w5cx"
const role = UserRole.Admin;
```

The value is controlled by the enum.

The Foundation Kit describes this as eliminating the **`admin` vs `Admin`** class of typo bugs.

# 2️⃣ `Partial`

`Partial<T>` makes **every property optional**.

### 💻 Code

```typescript id="b6uj1c"
interface User {
  id: number;
  name: string;
  email: string;
  role: UserRole;
}

type UpdateUser = Partial<User>;
```

Now this is valid:

```typescript id="4r2h2k"
const updateUser: UpdateUser = {
  email: "new@test.com",
};
```

We don't need to provide `id`, `name`, and `role`.

### 🇮🇳 Telugu

# 5️⃣ `Record` ⭐ Very Important

`Record` creates a **typed key-value map**.

This is the important senior-level example in your Foundation Kit.

### 💻 Code

```typescript id="34n7u9"
const credentials: Record<
  UserRole,
  {
    email: string;
    password: string;
  }
> = {
  [UserRole.Admin]: {
    email: "admin@test.com",
    password: "Admin@123",
  },

  [UserRole.User]: {
    email: "user@test.com",
    password: "User@123",
  },

  [UserRole.Viewer]: {
    email: "viewer@test.com",
    password: "Viewer@123",
  },
};
```

The source specifically uses this enum-keyed credentials pattern.

# 💼 Real-Time SDET Project Example

Imagine our application supports three roles:

```text id="v2xg1e"
Admin
User
Viewer
```

We have different credentials for each.

Instead of:


we create:

```typescript id="apqvne"
enum UserRole {
  Admin = "admin",
  User = "user",
  Viewer = "viewer",

```

and:

```typescript id="q8m4k1"
const credentials: Record<
  UserRole,

    email: string;

    password: "Admin@123",
  },
  [UserRole.User]: {
    email: "user@test.com",
    password: "User@123",
  },
  [UserRole.Viewer]: {
    email: "viewer@test.com",
    password: "Viewer@123",
  },
};
```

Then our test can do:

```typescript id="x4a0od"

await page.getByLabel("Username").fill(loginData.email);

await page.getByLabel("Password").fill(loginData.password);
```

# ⭐ Why is `Record<Enum, Type>` so powerful?

Suppose tomorrow application adds:

```typescript id="8y0h3p"
enum UserRole {
  Admin = "admin",
  User = "user",
  Viewer = "viewer",
  Manager = "manager",
}
```

But we forget to add Manager credentials.

Because our map is:

```typescript id="4gkmv0"
Record<UserRole, Credentials>;
```

TypeScript reports that the credentials map is missing the new role.

The Foundation Kit calls this **compile-time exhaustiveness**.

### 🇮🇳 Telugu

Idi chala important.

New role add chesam:

```text id="l6h3k1"
Manager
```

Credentials add cheyyadam marchipoyam.

`Record<UserRole, Credentials>` valla:

> **Compiler immediately missing Manager entry ani cheptundi.**

Plain object lo idi silent ga miss avvachu, and test runtime lo fail ayye chance undi.

# 🎯 Follow-up Questions Interviewer May Ask

### Q1. What is an enum?

> **“An enum defines a set of named constants.”**

Example:

```typescript id="u6n6j3"
enum Status {
  Passed = "passed",
  Failed = "failed",
}
```

---

### Q2. What is `Partial`?

> **“Partial makes all properties of an existing type optional.”**

```typescript id="q4d7w5"
type UpdateUser = Partial<User>;
```

---

### Q3. What is `Pick`?

> **“Pick selects specific properties from an existing type.”**

```typescript id="9c2e1h"
type UserInfo = Pick<User, "name" | "email">;
```

---

### Q4. What is `Omit`?

> **“Omit removes specific properties from an existing type.”**

```typescript id="5fj9zh"
type CreateUser = Omit<User, "id">;
```

---

### Q5. What is `Record`?

> **“Record creates a typed key-value map.”**

```typescript id="c3t1nr"
Record<UserRole, Credentials>;
```

---

### Q6. Why use `Record` with an enum?

### ⭐ Strong answer

> **“It gives compile-time exhaustiveness. If I add a new enum value, TypeScript forces me to add the corresponding test data or credentials.”**

---

### Q7. What is the difference between `Record` and a normal object?

**Answer:**

> “A normal object doesn't necessarily enforce that every expected key exists. `Record<Enum, Type>` can enforce that all enum members have corresponding values.”

# 🧠 Easy Memory Trick

Remember:

### **E-P-O-P-R**

**E → Enum = Eliminate magic strings**

**P → Partial = Properties optional**

**O → Omit = Out/remove**

**P → Pick = Pick required fields**

**R → Record = Required key-value map**

### 🔥 Super-simple memory

> **Enum = No magic strings**
> **Partial = Optional**
> **Omit = Remove**
> **Pick = Select**
> **Record = Map**
