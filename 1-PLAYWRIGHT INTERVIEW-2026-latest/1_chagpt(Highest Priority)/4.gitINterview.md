Here is the **complete Git and GitHub workflow for interviews**, from creating a branch to raising a Pull Request (PR), assigning a reviewer, resolving conflicts, and merging code. I'll explain in simple English with Telugu meanings and Playwright examples.

# **1. Real-time Git workflow in a company**

Imagine you are a QA Automation Engineer working on a Playwright project. Your task is to automate the login functionality.

**1. Pull latest code**

`git pull origin main`

**2. Create feature branch**

`git switch -c feature/login-test`

**3. Write and test code**

Playwright automation scripts

**4. Add, commit and push**

`git add .` → `git commit` → `git push`

**5. Raise Pull Request**

Feature branch → main

**6. Review, approve and merge**

Address comments and merge after approval

తెలుగులో: ముందుగా latest code తీసుకుంటాం. తర్వాత feature branch create చేసి code రాస్తాం. Testing చేసిన తర్వాత commit చేసి GitHub కి push చేస్తాం. తర్వాత PR raise చేసి reviewer approval తీసుకొని main branch లో merge చేస్తాం.

# **2. Step-by-step commands with explanations**

## **Step 1: Check Git status**

```
git status
```

**Interview answer:** “I use `git status` to check the current branch and identify modified, staged, and untracked files.”

తెలుగు: ఏ files modify అయ్యాయి, ఏ files కొత్తగా ఉన్నాయి అని తెలుసుకోవడానికి ఉపయోగిస్తాను.

## **Step 2: Get the latest code**

```
git switch main
git pull origin main
```

- `git switch main` — switches to the main branch.
- `git pull origin main` — downloads and integrates the latest changes from the remote `main` branch.

**Interview answer:** “Before starting my work, I switch to the main branch and pull the latest code to avoid working on an outdated version.”

తెలుగు: మనం పని మొదలుపెట్టే ముందు team members చేసిన latest changes తీసుకుంటాం.

## **Step 3: Create a feature branch**

```
git switch -c feature/login-test
```

**Interview answer:** “I create a separate feature branch so that my changes do not directly affect the main branch.”

తెలుగు: Main branch లో నేరుగా changes చేయకుండా, మన task కోసం separate branch create చేస్తాం.

Common branch naming examples:

- `feature/login-test`
- `bugfix/login-error`
- `hotfix/production-issue`

## **Step 4: Write and execute Playwright tests**

Example:

```
import { test, expect } from '@playwright/test';

test('User login', async ({ page }) => {
  await page.goto('https://example.com/login');

  await page.getByLabel('Email').fill('user@example.com');
  await page.getByLabel('Password').fill('password123');

  await page.getByRole('button', { name: 'Login' }).click();
});
```

Run your tests:

```
npx playwright test
```

**Interview answer:** “I implement the automation scripts, execute the tests, verify the results, and make sure the changes are ready before committing.”

తెలుగు: Code రాసిన తర్వాత tests run చేసి failures ఉన్నాయా లేదా check చేస్తాం. Example credentials ని real project లో secure test data తో replace చేయాలి.

## **Step 5: Stage your changes**

```
git add .
```

This stages all changes under the current directory, except ignored files.

To stage one specific file:

```
git add tests/login.spec.ts
```

**Interview answer:** “I use `git add` to stage the files I want to include in the next commit.”

తెలుగు: Commit చేయాలనుకున్న files ని staging area లోకి తీసుకొస్తాం.

## **Step 6: Commit your changes**

```
git commit -m "Added Playwright login test"
```

**Interview answer:** “A commit saves a snapshot of my staged changes in the local Git repository. I use a meaningful commit message to describe the changes.”

తెలుగు: Local repository లో changes కి version save చేస్తాం.

## **Step 7: Push the branch to GitHub**

```
git push -u origin feature/login-test
```

Here:

- `origin` — the remote repository name.
- `feature/login-test` — the branch being pushed.
- `-u` — sets the upstream tracking branch for future pushes.

**Interview answer:** “I push my committed feature branch to the remote repository so that my team can access the code and I can raise a Pull Request.”

తెలుగు: మన local commits ని GitHub లో ఉన్న remote branch కి upload చేస్తాం.

For later updates, you can usually run:

```
git add .
git commit -m "Updated login assertions"
git push
```

## **Step 9: Assign a reviewer and assignee**

On the right side of the Pull Request page, use the relevant fields:

- **Reviewers:** The teammate who should review your code.
- **Assignees:** The person responsible for handling the PR, based on the team's process.
- **Labels:** For categorizing the PR, such as `automation` or `bug`.

**Interview answer:** “I assign the appropriate reviewer so the code can be reviewed. I add an assignee and labels according to the team's workflow.”

తెలుగు: Code review చేయాల్సిన teammate ని reviewer గా select చేస్తాం.

## **Step 10: Handle reviewer comments**

Suppose your reviewer says that your locator should be more reliable.

You update your code locally and run the tests again:

```
git add .
git commit -m "Improved login locators"
git push
```

The existing PR updates automatically because you pushed changes to the same branch.

**Interview answer:** “If the reviewer requests changes, I update the code, rerun the tests, commit the fixes, and push them to the same branch. The existing PR is updated automatically.”

తెలుగు: Reviewer changes అడిగితే code update చేసి అదే branch కి push చేస్తాం. కొత్త PR అవసరం లేదు.

## **Step 11: Resolve a merge conflict**

A merge conflict occurs when Git cannot automatically combine competing changes.

First, update your feature branch with the latest main branch:

```
git fetch origin
git merge origin/main
```

If Git reports a conflict:

1. Open the conflicted files in VS Code.
2. Review the conflicting changes.
3. Choose or combine the correct code.
4. Save the resolved file.
5. Stage and commit the resolution.

```
git add .
git commit -m "Resolved merge conflict"
git push
```

**Interview answer:** “When a merge conflict occurs, I fetch the latest changes, merge the target branch into my feature branch, resolve the conflicting code, test it, commit the resolution, and push the updated branch.”

తెలుగు: రెండు branches లో ఒకే code భాగంలో conflicting changes ఉంటే, వాటిని manually resolve చేసి tests run చేసి push చేస్తాం.

## **Step 12: Approve and merge the PR**

After the reviewer approves your changes and required CI checks pass, an authorized person merges the PR according to the team's process.

Common merge options:

| Option                | Meaning                                                       |
| --------------------- | ------------------------------------------------------------- |
| Create a merge commit | Preserves the branch history and creates a merge commit       |
| Squash and merge      | Combines the PR's commits into one commit                     |
| Rebase and merge      | Replays commits onto the target branch without a merge commit |

**Interview answer:** “Once the PR is approved and all required checks pass, the PR is merged into the main branch using the merge strategy followed by the team.”

తెలుగు: Approval వచ్చిన తర్వాత, required tests pass అయితే PR ని main branch లో merge చేస్తాం.

## **Step 13: Update your local main branch**

After the PR is merged:

```
git switch main
git pull origin main
```

If your team deletes feature branches after merging, you can clean up your local branch:

```
git branch -d feature/login-test
```

**Interview answer:** “After merging, I update my local main branch to get the latest code and delete my local feature branch if it is no longer needed.”

తెలుగు: Merge అయిన తర్వాత latest main code తీసుకుని అవసరం లేని local feature branch delete చేస్తాం.

# **4. Complete interview answer: “Explain your Git workflow”**

You can use this answer directly in your interview.

In my project, we use Git for version control and GitHub for repository management and code reviews.

First, I check the current status using `git status`. Then I switch to the main branch and pull the latest code using `git pull origin main`.

Next, I create a feature branch for my task using `git switch -c feature/login-test`. I write and execute my Playwright automation scripts and verify that the tests are working correctly.

After completing the changes, I stage the files using `git add .`, commit them with a meaningful message using `git commit`, and push the feature branch to GitHub using `git push`.

Then I raise a Pull Request from my feature branch to the main branch. I provide a title and description and assign a reviewer.

If the reviewer requests any changes, I update the code, rerun the tests, commit the fixes, and push them to the same branch. If there are merge conflicts, I resolve them and verify the code.

Finally, after approval and successful required checks, the PR is merged into main. I then update my local main branch using `git pull origin main`.
