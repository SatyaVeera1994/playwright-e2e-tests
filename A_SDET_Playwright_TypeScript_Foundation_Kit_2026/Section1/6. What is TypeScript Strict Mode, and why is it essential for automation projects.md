# Q6. What is TypeScript Strict Mode, and why is it essential for automation projects?

The Foundation Kit defines `strict: true` as a **bundle of compiler safety checks**, including `strictNullChecks`, `noImplicitAny`, `strictFunctionTypes`, and `strictPropertyInitialization`. It especially emphasizes `strictNullChecks` because it catches `null`/`undefined` problems before they become confusing CI/runtime failures.

---

## ✅ English Interview Answer

> **“TypeScript strict mode is a set of compiler checks enabled using `strict: true` in `tsconfig.json`. It includes checks such as `strictNullChecks`, `noImplicitAny`, and others. For automation, `strictNullChecks` is especially useful because it forces us to handle `null` and `undefined` explicitly. This catches configuration and test-data issues at compile time instead of allowing them to cause cryptic runtime failures in CI.”**

### ⭐ Short Interview Answer

> **“Strict mode catches TypeScript problems early, especially null and undefined issues, before they reach test execution or CI.”**

---


The source explicitly recommends treating strict mode as mandatory for a maintainable framework.

# ❌ Without Strict Null Checking

```typescript id="z6x4p0"
const user = findUser(id);

console.log(user.name);
```

Possible situation:

```text id="y4j2r3"
findUser()
     ↓
undefined
     ↓
user.name
     ↓
💥 Runtime error
```

The Foundation Kit gives this exact pattern: a lookup returning `User | undefined` cannot safely be dereferenced without a guard.

---

# ✅ With Strict Null Checking

```typescript id="z8q2e4"
const user = findUser(id);

if (!user) {
  throw new Error(`User ${id} not found`);
}

console.log(user.name);
```

Now:

```text id="l5r3h2"
findUser()
    ↓
User | undefined
    ↓
Check
    ↓
User
    ↓
user.name ✅
```

TypeScript understands that after the `if` check, `user` is a valid `User`.

# 💼 Real-Time SDET Example — Environment Variables

This is **very important for your Playwright framework**.

Suppose we have:

```typescript id="9k4q8n"
const email = process.env.ADMIN_EMAIL;
```

TypeScript treats this as:

```typescript id="x2n7mz"
string | undefined;
```

Because the environment variable may not exist.

The Foundation Kit specifically highlights environment variables as a practical reason strict mode matters in fixtures.

---

## ❌ Unsafe Code

```typescript id="h3d8p2"
const email = process.env.ADMIN_EMAIL;

await page.getByLabel("Username").fill(email);
```

Potential problem:

```text id="q9x5j3"
ADMIN_EMAIL exists
       ↓
string ✅

ADMIN_EMAIL missing
       ↓
undefined ❌
```

---

# ✅ Better SDET Code

```typescript id="k2p5s8"
const email = process.env.ADMIN_EMAIL;

if (!email) {
  throw new Error("ADMIN_EMAIL is required");
}

await page.getByLabel("Username").fill(email);
```

Now the test fails immediately with a clear message:

```text id="q4j7v8"
ADMIN_EMAIL is required
```

Instead of getting some unrelated failure later in the test.

# 💻 Real Playwright Fixture Example

```typescript id="a8r2m5"
import { test as base } from "@playwright/test";

export const test = base.extend<{
  adminEmail: string;
}>({
  adminEmail: async ({}, use) => {
    const email = process.env.ADMIN_EMAIL;

    if (!email) {
      throw new Error("ADMIN_EMAIL is required");
    }

    await use(email);
  },
});
```

Then:

```typescript id="v4n8q1"
test("Admin Login", async ({ page, adminEmail }) => {
  await page.goto("/login");

  await page.getByLabel("Username").fill(adminEmail);
});
```

### Why this is good?

```text id="u7k2p9"
Environment
     ↓
Validate
     ↓
Missing? → Fail immediately ❌
     ↓
Available
     ↓
Playwright Test ✅
```

This fixture-validation pattern is directly shown in the Foundation Kit.
