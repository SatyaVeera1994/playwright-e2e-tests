# Q2. Interface vs Type — What is the difference?

The Foundation Kit specifically covers **interfaces vs type aliases** and the practical use of **`Omit`, `Partial`, and `Pick`** for keeping automation/API contracts maintainable.

---

## ✅ English Interview Answer

> **“Both `interface` and `type` can define the shape of objects in TypeScript. I generally use interfaces for object contracts that may be extended or implemented, especially for Page Objects and domain models. I use type aliases when I need unions, intersections, or utility types such as `Pick`, `Omit`, and `Partial`. In a large automation framework, I prefer deriving types instead of duplicating them because it keeps one source of truth.”**

### Short interview version

> **“Interface is mainly useful for object contracts and extension, while type is more flexible for unions, intersections, and derived types. I use both depending on the requirement.”**

# 🔍 Internal Concept — How it works

## 1. Interface

An interface describes the structure/contract of an object.

```typescript id="9k6n7a"
interface User {
  id: number;
  name: string;
  email: string;
}
```

Now:

```typescript id="0cvf9g"
const user: User = {
  id: 101,
  name: "Satya",
  email: "satya@test.com",
};
```

TypeScript checks that the object follows the `User` contract.

---

## 2. Interface can be extended

```typescript id="0y8s1p"
interface BasePage {
  navigate(url: string): Promise<void>;
}

interface LoginPage extends BasePage {
  login(username: string, password: string): Promise<void>;
}
```

So:

```text id="x3fqk0"
BasePage
   ↓ extends
LoginPage
```

This is very useful for Page Object frameworks.

---

# 3. Type Alias

A `type` can also describe an object:

```typescript id="z1z6i2"
type User = {
  id: number;
  name: string;
  email: string;
};
```

But `type` becomes especially useful when creating combinations.

### Union

```typescript id="g4h2hx"
type Browser = "chromium" | "firefox" | "webkit";
```

Now:

```typescript id="5m0k3v"
const browser: Browser = "chromium";
```

But:

```typescript id="qj0t6y"
const browser: Browser = "edge";
```

❌ TypeScript error.

# 🔥 Important: `Pick`, `Omit`, `Partial`

These are very important for SDET interviews.

---

## `Pick`

Existing interface nundi **specific properties select** chestundi.

```typescript id="b7zjkw"
interface User {
  id: number;
  name: string;
  email: string;
  role: string;
}
```

Suppose login test ki only `email` and `role` kavali.

```typescript id="y7n2ks"
type LoginUser = Pick<User, "email" | "role">;
```

Result:

```typescript id="z0z5td"
{
  email: string;
  role: string;
}
```

### Telugu

`Pick` = **Kavalasina fields pick cheyyadam.**

---

# `Omit`

Existing interface nundi unwanted properties remove chestundi.

```typescript id="9c4v7q"
type CreateUser = Omit<User, "id">;
```

Result:

```typescript id="k9q0s4"
{
  name: string;
  email: string;
  role: string;
}
```

### Real API example

Backend generates `id`, so create-user request lo `id` pampinchalsina avasaram ledu.

```text id="cv7bjs"
User Response
     ↓
Omit(id)
     ↓
CreateUser Request
```

### Telugu

`Omit` = **Unwanted fields remove cheyyadam.**

---

# `Partial`

Existing interface lo **all properties optional** chestundi.

```typescript id="4y8u2c"
type UpdateUser = Partial<User>;
```

Now:

```typescript id="gd8x7v"
const update: UpdateUser = {
  email: "new@test.com",
};
```

`name`, `id`, `role` mandatory kaavu.

### Telugu

`Partial` = **Every field optional.**

# 💼 Real-Time SDET Example

Suppose API automation lo user API undi.

Response:

```typescript id="x9i7qh"
interface UserResponse {
  id: number;
  name: string;
  email: string;
  role: string;
  createdAt: string;
}
```

### Create User

Backend `id` and `createdAt` generate chestundi.

So:

```typescript id="6n8k4r"
type CreateUserRequest = Omit<UserResponse, "id" | "createdAt">;
```

### Update User

Update API lo all fields mandatory kaavu:

```typescript id="0w1w1x"
type UpdateUserRequest = Partial<CreateUserRequest>;
```

### Get only authentication information

```typescript id="f0s8t4"
type LoginUser = Pick<UserResponse, "email" | "role">;
```

So one interface → multiple API contracts.

This follows the Foundation Kit's principle of using derived types rather than duplicating object shapes.

# 💻 Complete TypeScript + Playwright Example

```typescript id="h1y4kq"
import { test, expect } from "@playwright/test";

interface UserResponse {
  id: number;
  name: string;
  email: string;
  role: string;
  createdAt: string;
}

type CreateUserRequest = Omit<UserResponse, "id" | "createdAt">;

type UpdateUserRequest = Partial<CreateUserRequest>;

type LoginUser = Pick<UserResponse, "email" | "role">;

test("Create user API", async ({ request }) => {
  const user: CreateUserRequest = {
    name: "Satya",
    email: "satya@test.com",
    role: "user",
  };

  const response = await request.post("/api/users", {
    data: user,
  });

  expect(response.status()).toBe(201);
});
```

### What is happening?

```text id="8mnygl"
UserResponse
     │
     ├── Omit → CreateUserRequest
     │
     ├── Partial → UpdateUserRequest
     │
     └── Pick → LoginUser
```

**One source → multiple types.**

That is the important interview concept.

# 🎯 Follow-up Questions Interviewer May Ask

### Q1. Can interface extend another interface?

**Answer:**

> Yes. An interface can extend one or more interfaces.

```typescript id="xk9h2p"
interface A {
  id: number;
}

interface B extends A {
  name: string;
}
```

---

### Q2. Can type create a union?

**Answer:**

> Yes.

```typescript id="3w6s0f"
type Status = "PASS" | "FAIL" | "SKIPPED";
```

---

### Q3. What is `Pick`?

> `Pick` selects specific properties from an existing type.

```typescript id="j7x4m8"
type UserInfo = Pick<UserResponse, "name" | "email">;
```

---

### Q4. What is `Omit`?

> `Omit` removes specific properties from an existing type.

```typescript id="q6z8nd"
type CreateUser = Omit<UserResponse, "id">;
```

---

### Q5. What is `Partial`?

> `Partial` makes all properties optional.

```typescript id="8kq2vn"
type UpdateUser = Partial<UserResponse>;
```

---

### Q6. Why shouldn't you duplicate interfaces?

**Answer:**

> “Duplicated interfaces can become inconsistent when the original domain model changes. Derived types automatically stay synchronized with the source type.”

---

### Q7. Which one do you prefer: Interface or Type?

### Strong interview answer:

> **“I don't treat it as a strict either-or rule. I use interfaces for object contracts and extensible Page Object or domain models, and type aliases for unions, intersections, and derived types. The important thing is consistency within the framework.”**

This is a better answer than saying **“Interface is always better”** or **“Type is always better.”**

# 🧠 Easy Memory Trick

Remember:

### **I + T + POT**

**I → Interface = Object contract**

**T → Type = Type combinations**

**P → Pick = Keep selected fields**

**O → Omit = Remove fields**

**T → Partial = Turn fields optional**

Actually, for `Partial`, remember:

> **Partial = Possible/Optional**

### One-line memory:

> **Pick = Take, Omit = Remove, Partial = Optional.**
