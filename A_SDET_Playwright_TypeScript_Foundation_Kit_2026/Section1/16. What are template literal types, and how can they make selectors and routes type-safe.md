# Q16. What are template literal types, and how can they make selectors and routes type-safe?

**Level: Senior**

This is a strong Senior-level TypeScript question because it shows how you can make **string conventions enforceable by the compiler**, instead of relying only on comments or coding guidelines.

---

## ✅ 1. English Interview Answer

> **“Template literal types, introduced in TypeScript 4.1, allow us to create string types using template literal syntax. They can combine literal strings with other types or unions to define valid string patterns. In an SDET framework, I can use them to create type-safe test-ID selectors, API route patterns, and event-handler names. For example, I can define a selector as `[data-test="${string}"]`, so a value like `[data-test="submit"]` is valid while `#submit` is rejected by the compiler. The key benefit is that we can encode protocol and naming conventions directly into the type system.”**

### ⭐ Short Interview Answer

> **“Template literal types allow us to define patterns for valid strings at compile time. In Playwright, they can make selectors, routes, and event names type-safe.”**

# 🔍 3. Internal Concept — How It Works

Normal TypeScript:

```typescript id="9q7k3m"
type Greeting = string;
```

This accepts **any string**:

```typescript id="8w2f6n"
const a: Greeting = "Hello";
const b: Greeting = "ABC";
const c: Greeting = "Anything";
```

But sometimes we want a **specific string pattern**.

Template literal types allow:

```typescript id="t6v3pz"
type Greeting<T extends string> = `Hello ${T}`;
```

Now:

```typescript id="d1f8ra"
type WorldGreeting = Greeting<"World">;
```

becomes:

```typescript id="k9m2xs"
"Hello World";
```

So TypeScript can understand **patterns inside strings**.

# 🎯 4. Playwright Real-Time Example — Type-Safe Test IDs

Suppose your framework follows this convention:

```html
<button data-test="submit"></button>
```

We can define:

```typescript id="3d4jwp"
type TestIdSelector = `[data-test="${string}"]`;
```

Now:

```typescript id="7p1m4c"
function byTestId(selector: TestIdSelector) {
  return selector;
}
```

### ✅ Valid

```typescript id="a8x6nf"
byTestId('[data-test="submit"]');
```

### ❌ Invalid

```typescript id="z5n3ku"
byTestId("#submit");
```

The compiler rejects it because:

```text id="m7c2ra"
#submit
  ↓
doesn't match
  ↓
[data-test="${string}"]
```

# 💻 5. Type-Safe Route Patterns

This is another excellent SDET example.

Suppose your application has:

```text id="p2w8fk"
/users/123/orders
/users/456/orders
```

We can define:

```typescript id="z6k1mt"
type UserOrderRoute = `/users/${number}/orders`;
```

Now:

```typescript id="v3r7nx"
const validRoute: UserOrderRoute = "/users/42/orders";
```

### ✅ Valid

```text id="f4s8wc"
/users/42/orders
```

### ❌ Invalid

```typescript id="r5j2bx"
const wrong: UserOrderRoute = "/users/abc/orders";
```

Because `abc` isn't a number.

# 🧩 7. Intrinsic String Helpers

Template literal types can also be combined with built-in string manipulation types:

- `Uppercase`
- `Lowercase`
- `Capitalize`
- `Uncapitalize`

Example:

```typescript id="u6v9dx"
type Event = "click" | "submit" | "change";
```

We can create:

```typescript id="b1s4kp"
type HandlerNames = {
  [E in Event as `on${Capitalize<E>}`]: () => void;
};
```

TypeScript generates:

```typescript id="w3m7qa"
type HandlerNames = {
  onClick: () => void;
  onSubmit: () => void;
  onChange: () => void;
};
```

# 🎯 10. Follow-up Questions Interviewers May Ask

## Q1. Since which TypeScript version are template literal types available?

> **“Template literal types were introduced in TypeScript 4.1.”**

---

## Q2. What's the difference between runtime template literals and template literal types?

### Runtime:

```typescript id="c6m9va"
const name = "Satya";

const message = `Hello ${name}`;
```

This creates an actual JavaScript string.

### Type level:

```typescript id="n3p7kx"
type Message = `Hello ${string}`;
```

This defines a **type pattern**.

### ⭐ Answer:

> **“Runtime template literals create strings; template literal types define allowed string patterns at compile time.”**

---

## Q3. Can template literal types validate runtime data?

> **“No. They provide compile-time type checking. They don't perform runtime validation of external data.”**

This is important.

For API data coming from outside:

```text id="v5r8yp"
External data
     ↓
Runtime validation
     ↓
TypeScript type
```

Don't assume template literal types alone validate runtime data.

---

## Q4. What are `Capitalize` and `Uppercase`?

> **“They are intrinsic string manipulation types that transform string literal types at compile time.”**

Example:

```typescript id="f7m2qd"
type A = Capitalize<"user">;
// "User"

type B = Uppercase<"user">;
// "USER"
```
